# mfe-pot-dashboard-mfe

## What this is

The **MSCA-D** frontend for the mfe-pot Government of Canada MFE proof-of-technology: 360° cross-benefit overview, payment history, correspondence, and "tell us once" profile maintenance. Federated as a remote into `mfe-pot-msca-shell`; also exposes a standalone payment-history widget embedded directly into `mfe-pot-life-events-mfe`, and embeds job-bank's job-applications widget and employment-insurance's EI-reporting-status widget in its own overview, behind the `dashboard-overview-cross-domain-widgets` Unleash flag (host-mediated via `mfe-pot-msca-shell` — see the platform repo's CLAUDE.md "Federation" and "Design principles" sections) — the one app in the family that's both a widget *source* and a widget *consumer*.

## What's in this repo

- `apps/dashboard-mfe` — the frontend, federated on port `4201` in local dev. Repo directory, Nx project, federation identity (`federation.config.mjs`'s `name`), Docker image, and Helm chart/release are all named `dashboard-mfe` — the `-mfe` suffix disambiguates this internal federated remote from either host app's own front-door name (see the meta repo's `../CLAUDE.md`). The underlying business-domain naming (Nx `scope:dashboard` tag, `libs/data-access`, CMS content keys) deliberately stays un-suffixed — that's domain identity, not hosting identity. `apps/dashboard-mfe/src/app/*.tsx` holds every component directly (`App.tsx`, `Overview.tsx`, `PaymentHistory.tsx`, and the smaller `WhatsNewList.tsx`/`NeedsAttentionList.tsx`/`ConsiderThisList.tsx`) — no separate `libs/<name>/feature-*` library the way this repo had before converting to React (see the platform repo's CLAUDE.md, "Components live in the app").
- `apps/dashboard-bff` — dashboard's dedicated BFF (port `3004`), serving its own local payments/correspondence data (`src/data.ts`, the same in-memory-stub pattern `job-bank-bff`/`employment-insurance-bff` use for their own domains). Never calls another BFF (see the platform repo's CLAUDE.md "Design principles" section) — used to, via a `getBenefitOverview` fan-out to `job-bank-bff`/`employment-insurance-bff` (`overview.ts`, `/api/overview`), deleted once that turned out to violate the "BFFs must not call each other" principle *and* have zero real consumers left. **Not** suffixed `-mfe` — no naming collision to disambiguate, no reason to touch it.
- `libs/data-access` — dashboard's `BenefitOverviewApiClient`/`PaymentHistoryApiClient` interfaces + `Http*` implementations. The one library that stayed separate when this repo's feature libs folded into `apps/dashboard-mfe/src/app/`.
- `charts/dashboard-mfe` — deploys the frontend+BFF pair as one Helm release, depending on both platform-repo library charts (`mfe-frontend-lib`, `mfe-backend-lib`).

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-auth-server`, `shared-content-client`, `shared-federation-config`, `shared-federation-runtime`, `shared-i18n`, `shared-locale-sync`, `shared-runtime-config`, `shared-session-cache`, `shared-ui-scds-core` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`). GCDS has been removed from the family entirely (see the platform repo's CLAUDE.md) — no wrapper package for SCDS either, `shared-ui-scds-core`'s custom elements (`scds-card`, `scds-heading`, `scds-notice`, `scds-badge`, and more) are consumed directly via JSX, same as every other app.

## Repo-specific things worth knowing

- **`dashboard-bff` is a self-contained leaf service, same shape as `job-bank-bff`/`employment-insurance-bff`** — it used to be architecturally different (a fan-out aggregator for `activeApplications`/`jobApplications`/`eiReportingStatus`, composing the other two BFFs over real HTTP with a partial-failure contract), but that fan-out was deleted once it violated "BFFs must not call each other" (see the platform repo's CLAUDE.md "Design principles" section) and turned out to have zero real consumers left besides its own tests. `payments`/`correspondence` are served from `dashboard-bff`'s own local `data.ts` (no upstream, so always succeeds barring a Redis outage) — see "Known, accepted tradeoff" note below. The cross-domain content that fan-out used to feed (job applications, EI reporting status) is composed in the browser instead now — see `CrossDomainWidgetTile` further down.
- **The Helm chart carries no other domain's BFF URL at all anymore** — `dashboard-bff`'s `backend.env` used to have `JOB_BANK_BFF_URL`/`EMPLOYMENT_INSURANCE_BFF_URL` pointing at cross-Helm-release in-cluster Service DNS, removed alongside the fan-out that used them. `dashboardBffBaseUrl` on the frontend side is unaffected: `/api`, a same-origin Ingress path rule, since that call is browser-to-server. The frontend's `runtimeConfig` now also carries `unleashFrontendApiUrl`/`unleashFrontendApiToken` (Unleash's Frontend API, browser-reachable, gating the cross-domain widget tiles — see the platform repo's CLAUDE.md "Design principles" section).
- **`strapiBaseUrl` now points at `mfe-pot-platform`'s real `charts/strapi` Ingress hostname** (`http://cms.mfe-pot.local`, browser-to-server, not in-cluster Service DNS — confirmed live).
- **Payments/correspondence used to be served by a separate `client-profile-service` (`mfe-pot-platform`) — removed.** That service had no Helm chart, so its one caller (`dashboard-bff`) 502'd in any real deployment. Its data now lives directly in `dashboard-bff`'s own `src/data.ts`, the same in-memory-stub pattern `job-bank-bff`/`employment-insurance-bff` already use — `HttpPaymentHistoryApiClient` still calls `dashboard-bff`'s `/api/payments`, unchanged, just no longer a proxy. **Known, accepted tradeoff**: `client-profile-service` existed specifically so this data was one shared source across all three domain BFFs (its own doc comment said so); folding it into `dashboard-bff` makes it dashboard-only, narrowing the not-yet-built "tell us once" cross-service demo beat (`../TODO.md`) — flagged there as needing a redesign, not silently dropped.
- **`federation.config.mjs`'s `exposes` map has a second entry beyond the usual `./Component`**: `./PaymentHistoryWidget` (`PaymentHistory.tsx`, exported as `DashboardFeaturePaymentHistory` — that exact name matters, `mfe-pot-msca-shell`'s `routes.tsx` resolves the widget module by it). There's no `./RemoteProviders` entry anymore — `PaymentHistory.tsx` is fully self-configuring (fetches its own runtime config, builds its own `HttpPaymentHistoryApiClient`) whether it's rendered by this app's own `Overview`/`App` or embedded remotely, so there's no host-provided-providers pairing left to carry across the federation boundary. If you ever move or rename `PaymentHistory.tsx`, this is the file that breaks first (`FsPath ... does not exist`), not `tsconfig.app.json`. The same applies to `./Component` itself — both `exposes` paths must point at `apps/dashboard-mfe/...`, not a stale pre-rename `apps/dashboard/...`.
- **`Overview.tsx` renders `WhatsNewList`/`NeedsAttentionList`/`DashboardFeaturePaymentHistory`/`ConsiderThisList` unconditionally** — matching `docs/msca-screenshots/dashboard.png`'s widget set exactly — **plus two feature-flagged cross-domain widget tiles**: job-bank's `JobApplicationsList` and employment-insurance's `ReportingStatus`, loaded via the generic `useWidgetLoader('job-applications'|'ei-reporting-status')` (`shared-federation-runtime`, provided by `mfe-pot-msca-shell`'s `WIDGET_REGISTRY`) through a small `CrossDomainWidgetTile` wrapper, gated behind the `dashboard-overview-cross-domain-widgets` Unleash flag (`useFeatureFlag`, `@tn4consulting/shared-feature-flags` — default off, so the page matches the reference screenshot until the flag is rolled out). This used to also render a "My Tasks" list (`TasksList.tsx`, fed by `dashboard-bff`'s now-deleted `getBenefitOverview` fan-out) and the same two widgets unconditionally; all three were dropped since none appear in the reference screenshot, each widget rendering instead on its own owning app's page (`mfe-pot-job-bank-mfe`'s/`mfe-pot-employment-insurance-mfe`'s own `App.tsx`, unaffected either way). The two widgets are back now, restored the compliant way — see the platform repo's CLAUDE.md "Design principles" section for why the fan-out that used to feed them was deleted rather than kept as an exception. "My Tasks" itself stays dropped: no owning page, and its content was always just a restatement of the EI claim/reporting-status signals `ReportingStatus` already surfaces. When the flag is on, `Overview.tsx` also opens its own OTel root span and passes a `parentTraceparent` prop into `DashboardFeaturePaymentHistory` and both `CrossDomainWidgetTile`s, so all three widgets' BFF calls join one trace — see the platform repo's CLAUDE.md "Observability" section.
- **`Overview.tsx` also directly renders `DashboardFeaturePaymentHistory`** (moved here from `App.tsx`, in a `.dashboard-overview__grid` two-column layout alongside `NeedsAttentionList` — matches `docs/msca-screenshots/dashboard.png`'s "Needs Attention"/"Payments Activity" side-by-side layout). `PaymentHistory.tsx` now also wraps itself in a persistent-shadow card (matching `scds-card`'s own look) and renders an "Actions" column plus a "View payment history" link below the table, closing the gap with the reference screenshot's card. This is a pure render-location/presentation change, not a contract change: `PaymentHistory.tsx`'s export name/zero-prop signature/self-configuring behavior are untouched, so its federation exposure as `./PaymentHistoryWidget` (see above) is unaffected.
- **`scds-card`/`scds-table` now carry a persistent `box-shadow: var(--scds-shadow-sm)`** (`shared-ui-scds-core`, not this repo) instead of only showing a shadow on link-card hover — every card-shaped widget on this page (`NeedsAttentionList`, `ConsiderThisList`, `PaymentHistory`'s own card wrapper) picked this up for free, matching `docs/msca-screenshots/dashboard.png`'s elevated card look.
- **`TasksList.tsx` sets `scds-multi-column-list`'s `items`/`columns` imperatively** (`document.createElement` + direct property assignment), not via JSX — those props are non-primitive (arrays), and Stencil never reflects them to/from a DOM attribute at all. See the platform repo's CLAUDE.md "GC Design System" section for the general rule this follows (same pattern as job-bank's `FeatureSearch.tsx`).
- **The payment-history widget's headings/table labels/status text are now CMS-driven** (`dashboard.payment-history.*` keys, batch-fetched via `ContentClient.getPageContents` on mount and re-fetched on cross-remote locale change via `@tn4consulting/shared-i18n`'s `useLocale`) — previously static English mock text. The underlying payment records themselves (`dashboard-bff`'s `data.ts`) are still test data by design; only the surrounding labels moved to CMS. Currency formatting (`$${amount.toFixed(2)}`) is still locale-naive — a narrower, separately-tracked gap (see `../TODO.md`). No component keeps its own hardcoded fallback text anymore — `createContentClient(strapiBaseUrl, assetBaseUrl)` (`content-client.ts`) always wraps Strapi with a `FallbackContentClient` backed by `public/assets/content-fallback/{en,fr}.json`, so a CMS outage degrades to bilingual fallback content instead of English-only text; see the platform repo's CLAUDE.md "i18n" section for the full mechanism.
- **CI** (`.github/workflows/ci.yml`): lint/test/build (including `dashboard-bff`'s separately-run `eslint:lint` target), then builds both images, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves. The `/api/correspondence` smoke check omits the `sub` query param deliberately (asserts a 400, not a 404) — proves the request reached the Express app. Also runs `check:versions`/`check:boundaries` (`@tn4consulting/shared-platform-standards`) before the lint/test/build step. See `README.md` for local install/serve/build/Docker/Helm instructions.
